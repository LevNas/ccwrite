# 日本語文章ルーター

日本語の文章を書く・直す・添削するとき、宛先とチャネルに合わせて書き分けるためのスキル。
文章の品質規範（論証の厳密さ、LLM っぽい表現の禁止、冗長の排除など）は `japanese-tech-writing` に従う。本スキルはその上物として、チャネルの振り分け、相手区分による敬語と開示範囲の調整、テンプレートの蓄積、着手前の質問を担う。

## 適用の前提

- 文章の品質規範は `japanese-tech-writing` を正本とする。本スキルに規範を複製しない。規範の本文が要るときは同スキルを読む。
- 作業中のリポジトリに固有の文体・記法ルール（例: 敬体統一、em ダッシュや中黒の様式）があれば、そちらを優先する。
- 文体（敬体か常体か）はリポジトリの文体ルールが決める。本スキルはそれを下限として、宛先に応じて尊敬語・謙譲語へ引き上げるだけにする。文体ルールが無いリポジトリでは、周りの文章に合わせる（文体ルールを置きたいときは、ccharness の tone テンプレートで書き出せる）。
- チーム共有の常時ルール（トーン配慮、避ける表現・採用する表現、Markdown 記法）が読み込まれている環境では、それにも従う。

## まず確認すること（不明なら質問する）

文章を書く・直す前に、**チャネル**と**相手区分**が依頼文・本文から一意に決まるかを点検する。

- 一意に決まるなら、質問せずそのまま進める（過剰な質問はしない）。
- 決まらないなら、着手前に短く質問する。最小限の問いにする。
  - 「これは誰宛てですか（社内／顧客／パートナーなど）」
  - 「どのチャネルですか（メール／チャット／掲示板／ドキュメント）」
  - 「用件は何ですか（一次連絡／依頼／報告／お詫び など）」
- **対外（顧客・パートナー）が絡む可能性があるときは、推定で進めず必ず確認する。** 宛先を取り違えると開示範囲を誤り、影響が大きいため。
- 添削（渡された文章の確認）は、宛先が本文から読み取れないことが多い。ここが質問の主戦場になる。

## チャネル別ルーティング

| チャネル | 効かせる中心 | 弱める・外す | 書式・敬語 |
|---|---|---|---|
| ドキュメント（設計・運用資料） | japanese-tech-writing の全節 | （原則すべて適用） | 見出し・箇条書き。リポジトリの文体と Markdown 規約に従う |
| チャット（Teams・Slack など） | LLM っぽい表現の禁止、冗長の排除 | 一文一行、脚注、パラグラフライティング | 短く。場に合わせた口調。宛先メンションに注意 |
| 掲示板 | LLM っぽい表現の禁止、冗長の排除、見出しの付け方 | 脚注 | 公開前提の言い回し。読み手が広い前提で前提説明をやや厚く |
| メール | 論証の厳密さ、冗長の排除 | 脚注 | 敬語。宛名・挨拶・結び。相手区分で敬語の厚みを変える |
| 添削（渡された文章の確認） | 依頼された観点＋ japanese-tech-writing | 相手が指定した以外の構造改変は控えめに | 元の文体を尊重しつつ規範に寄せる。宛先が不明なら上記のとおり質問する |

## 改行と段落（Markdown で描画されるチャネル）

段落と改行は役割が異なる。段落は意味のまとまり（論証の一歩）であり、改行は段落内の表示の調整である。日本語の書き言葉の慣習では段落に確立した規則がなく、「目やすめ」程度に使われることも多い。だからこそ技術文書では、パラグラフライティング（`japanese-tech-writing` の「段落と論証の構成」が正本）を意図的に採用し、1 段落 1 トピックで書く。

Markdown が HTML に描画されるチャネル（GitHub や GitLab のドキュメントや issue、note の記事など）では、ソース上の改行と描画結果が一致しない。意図に合わせて次のとおり書き分ける。

| 意図 | Markdown の書き方 | 描画結果 |
|---|---|---|
| 段落を変える（話題を変える） | 空行を 1 行入れる | 新しい段落（`<p>`） |
| 段落内で改行を見せる（一文一行など） | 行末に半角スペース 2 つ + 改行 | `<br>` |
| 表のセル内で改行を見せる | `<br>` タグを書く（行末スペースは効かない） | `<br>` |
| ソース上の区切りだけ（描画は連結でよい） | 単純な改行 | 前後が連結されて 1 行になる |

- 単純な改行は描画で改行にならない。読み手に改行を見せたいなら、行末スペース 2 つか `<br>` を明示する。
- 作業中のリポジトリに Markdown 規約（一文一行の徹底、表セルの記法など）があれば、そちらを優先する。
- 描画で崩れる書き方の詳細と検査は `markdown-style` にある。

### 折り返し位置は文節境界で選ぶ（budouX）

表のセルや図のラベル、スライドのように幅が限られる場所で長い文を折り返すときは、任意の位置で切らず、budouX の分割結果（文節境界）から折り返し位置を選ぶ。

- 文節候補の一覧: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/budoux-wrap" --venv "${CLAUDE_PLUGIN_DATA}/venv" --phrases "対象テキスト"`（1 行 1 文節で出力）。
- 折り返し済みテキストの生成（表セル向け）: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/budoux-wrap" --venv "${CLAUDE_PLUGIN_DATA}/venv" --width 15 --sep '<br>' "対象テキスト"`。本文の行内改行にするなら `--sep` の代わりに `--md`（行末スペース 2 つ + 改行）。
- budoux が見つからないと `budoux-wrap` はその旨を表示して終わる。初回だけ、PyPI から budoux を入れてよいかを利用者に確かめ、承諾を得てから `bash "${CLAUDE_PLUGIN_ROOT}/scripts/setup-budoux" "${CLAUDE_PLUGIN_DATA}/venv"` を実行する。この venv はプラグインの更新では残り、アンインストールで消える。
- budouX を使わない・使えない環境では、同じ基準（文節の切れ目、助詞の直後など）を自分で判断して折る。

## 相手区分（敬語と開示範囲）

| 相手区分 | 敬語 | 開示範囲 | 注意 |
|---|---|---|---|
| 社内 | 文体ルールのとおり | 社内前提でよい | 部内の共通語・略語は通じる範囲で使う |
| 特定コミュニティ | 文体ルールのとおり | 参加者前提 | 前提説明をやや厚く。内輪すぎる略語は展開する |
| 顧客 | 敬語を厚く | 必要最小限 | 社内の略語・内部事情を出さない。用件と次アクションを明確に |
| パートナー企業 | 顧客に準じる | 契約・NDA の範囲内 | 開示可否が曖昧なら確認する。共同作業の役割分担を明確に |

## テンプレートの運用

やり取りを重ねる中でテンプレートを育てる。最初は空でよい。

- 置き場所: 利用者設定の `templates_dir`（現在の値: `${user_config.templates_dir}`）。値が空のとき、または `user_config.templates_dir` という記法が置き換わらずに残っているときは未設定なので、既定の `${CLAUDE_PLUGIN_DATA}/templates` を使う。
- 既定の置き場に初めて保存するときは、一度だけ「この置き場はプラグインをアンインストールすると消えます。残したいときは `/config` で ccwrite の `templates_dir` に private リポジトリ内のディレクトリを指定してください」と伝える。テンプレートには社内の相手や用件が入るため、public なリポジトリは勧めない。
- 構成: `<置き場>/<チャネル>/`（`mail/`、`chat/`、`board/`、`doc/`）。フォルダは初回保存時に作る。
- 命名: `<相手区分>-<用件>.md`（例: `mail/顧客-障害一次連絡.md`、`mail/パートナー-日程調整.md`、`chat/社内-作業完了報告.md`）。
- 使い方: 同種の相手・用件のとき、該当テンプレートを下敷きにして差分だけ埋める。
- テンプレート自体も `japanese-tech-writing` の規範に沿わせる。
- メールは「状況に応じてテンプレートを使いながら対外的なやり取りをする」用途を主に想定する。

## 分岐とテンプレートの育て方

「育てる」は自律学習ではなく、提案と承認を挟む蓄積とする。

- 文面が確定し、今後も使えそうなとき、「テンプレート化しますか」と提案する。承認後にテンプレートの置き場へ保存する。
- 新しいチャネルや相手区分が繰り返し現れたら、テンプレートの置き場にフォルダを足す提案をする。ルーティング表そのものを変えたいときは、利用者に伝えるだけにする（表はプラグインの一部で、更新で上書きされるため）。
- **勝手に増やさない。** 提案、承認、追記の順を守る。

## まとめ添削役（サブエージェント）との連携

下書きを複数まとめて直したいときは、サブエージェント `jp-copy-editor` を使う。

- `jp-copy-editor` は本スキルと `japanese-tech-writing` を基準に、各下書きを直して返す。
- サブエージェントは実行中に利用者へ質問できない。宛先・チャネル・相手区分が不明な点は、推測で確定せず「質問」として返却物にまとめる。メイン側（この会話）でその質問を利用者に取り次ぐ。
